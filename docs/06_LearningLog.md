## 2026-09-08_Railway本番環境でのMixed Contentエラー

### 症状
- ローカル(Sail)では正常動作するfetch()ベースのAPI通信(人物クイック登録モーダル)が、
  Railway本番環境でのみ「通信エラーが発生しました」と表示され失敗する
- Railwayのアプリログにはリクエストの痕跡が一切残らない
- ブラウザの開発者ツールでMixed Contentエラーを確認して発覚
  (`https://...`のページ内から`http://...`宛のフォーム送信が発生していた)

### 原因
Railway(および多くのPaaS)では、外部からのHTTPS通信を手前のロードバランサ/プロキシが
一旦HTTPに変換してからアプリのコンテナへ転送する構成になっている。
Laravel側はこの転送後のHTTPリクエストしか見えないため、「このアプリはHTTPで動いている」
と誤認識し、`route()`やフォームのaction URLをすべて`http://`で生成してしまう。

ブラウザは「HTTPSページ内からHTTPへの送信」をセキュリティ上ブロックするため、
リクエストがサーバーに届く前に握りつぶされ、サーバーログにも何も残らない。

### 対処
`RouteServiceProvider.php`の`boot()`冒頭に以下を追加し、本番環境では常にHTTPSとして
URLを生成するよう強制した。

\```php
if (config('app.env') === 'production') {
    URL::forceScheme('https');
}
\```

### 教訓
- ロードバランサ/プロキシを挟むデプロイ環境(Railway, Heroku, AWS ALB配下のECS等)では、
  `URL::forceScheme('https')`(または`TrustProxies`ミドルウェアの設定)が定番の対処法。
  今後別のクラウド環境にデプロイする際も、最初からこの設定を入れておくと同じハマりを回避できる。
- fetch()系のAPI通信がブラウザ側でブロックされるケースは、サーバーログを追っても
  何も見つからないため気づきにくい。「サーバーに届いているか」をブラウザの開発者ツールの
  Networkタブ/Consoleで確認するのが切り分けの近道。
